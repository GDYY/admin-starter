# 设备巡检管理系统 · 设计说明

> 这是本项目的需求与技术设计文档。**它本身就是作品的一部分**——面试官打开仓库会先看 README 和 docs，一份结构清晰的设计文档，比多写两个页面更能证明你「懂业务、能落地」。

---

## 一、业务背景

工厂、园区、写字楼的设备（电机、水泵、配电柜、空压机……）需要**定期点检**，提前发现隐患，避免非计划停机。

**现状痛点（这是简历上要讲的故事）**：

- 靠纸质点检表和 Excel 记录，容易漏检、补签
- 历史数据散落，查不到某台设备的故障规律
- 主管无法实时知道「今天该巡检的巡检完了没有」
- 发现异常后，从上报到处理没有闭环

**本系统解决**：把点检标准数字化，任务自动下发，结果实时汇总，异常自动闭环。

---

## 二、角色与权限

| 角色 | 能做什么 |
|---|---|
| **设备管理员** | 维护设备台账、配置点检项、制定巡检计划 |
| **巡检员** | 查看今日任务、执行点检、录入结果、上报异常 |
| **主管 / 领导** | 查看统计看板、巡检完成率、异常趋势 |

> 练手阶段先不做真实权限，`status` 字段和按钮级权限留作后续练习。

---

## 三、核心业务流程

```
维护设备台账
      ↓
按设备类型配置点检项（标准）
      ↓
制定巡检计划（哪台设备、什么频率、谁负责）
      ↓
系统按计划生成「今日巡检任务」
      ↓
巡检员逐项点检 → 录入结果（正常/异常/数值）
      ↓
有异常 → 自动生成异常记录 → 通知处理 → 闭环
      ↓
数据汇总 → 统计看板
```

## 四、数据表设计

### 4.1 `device` 设备台账

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint PK | 主键 |
| device_code | varchar(50) | 设备编号，唯一，如 `EQ-2026-001` |
| device_name | varchar(100) | 设备名称 |
| category | varchar(50) | 设备类型（电机/水泵/风机/配电柜/空压机） |
| location | varchar(100) | 安装位置 |
| model | varchar(100) | 规格型号 |
| manufacturer | varchar(100) | 生产厂商 |
| purchase_date | date | 采购日期 |
| status | tinyint | 1=正常 2=停用 3=维修中 4=报废 |
| manager | varchar(50) | 责任人 |
| remark | varchar(255) | 备注 |
| created_at | datetime | 创建时间 |
| updated_at | datetime | 更新时间 |

索引建议：`device_code` 唯一索引，`category`、`status` 普通索引。

### 4.2 `inspect_item` 点检项（标准）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint PK | |
| item_name | varchar(100) | 点检项名称，如「油位检查」 |
| category | varchar(50) | 适用的设备类型（电机/水泵…） |
| check_type | tinyint | 1=正常异常 2=数值录入 3=文字描述 |
| unit | varchar(20) | 单位（数值型用），如 ℃、MPa |
| min_value | decimal(10,2) | 正常范围下限 |
| max_value | decimal(10,2) | 正常范围上限 |
| standard | varchar(255) | 判定标准描述 |
| sort | int | 显示顺序 |
| status | tinyint | 1=启用 0=停用 |

> **设计说明**：点检项按「设备类型」配置，同类型设备共用一套标准。这样避免了设备与点检项的多对多中间表，逻辑也符合现场实际。

### 4.3 `inspect_plan` 巡检计划

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint PK | |
| plan_name | varchar(100) | 计划名称 |
| device_id | bigint FK | 关联 `device.id` |
| frequency | tinyint | 1=每日 2=每周 3=每月 |
| executor_id | bigint | 执行人 |
| start_date | date | 生效开始 |
| end_date | date | 生效结束 |
| status | tinyint | 1=启用 0=停用 |

### 4.4 `inspect_record` 巡检记录（主表）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint PK | |
| plan_id | bigint FK | 关联计划 |
| device_id | bigint FK | 关联设备 |
| executor_id | bigint | 实际执行人 |
| inspect_time | datetime | 巡检时间 |
| result | tinyint | 1=全部正常 2=存在异常 |
| abnormal_count | int | 异常项数量 |
| remark | varchar(255) | 备注 |

### 4.5 `inspect_record_detail` 巡检记录明细（从表）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint PK | |
| record_id | bigint FK | 关联 `inspect_record.id` |
| item_id | bigint FK | 关联 `inspect_item.id` |
| item_name | varchar(100) | 冗余存名称，防历史数据被改 |
| check_value | varchar(50) | 录入值（正常/异常，或数值） |
| is_abnormal | tinyint | 1=异常 0=正常 |
| remark | varchar(255) | 异常描述 |

> **设计说明**：主从表结构。冗余 `item_name` 是常见做法——点检项以后改名，历史记录仍要显示当时的名字。

### 4.6 `abnormal` 异常处理（可选，第二阶段做）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint PK | |
| record_id | bigint FK | 来源巡检记录 |
| device_id | bigint FK | |
| description | varchar(255) | 异常描述 |
| level | tinyint | 1=一般 2=严重 3=紧急 |
| handler | varchar(50) | 处理人 |
| status | tinyint | 1=待处理 2=处理中 3=已闭环 |
| handle_result | varchar(255) | 处理结果 |

## 五、接口列表（RESTful）

### 5.3 巡检计划

| 方法 | 路径 | 说明 |

| 方法 | 路径 | 说明 |

### 5.5 统计看板

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/dashboard/overview` | 概览：设备总数、今日应巡检、已完成、异常数 |

## 七、开发顺序（建议）

**第一阶段：把「设备台账」做透（预计 3–4 天）**

设备台账是**最标准的 B 端 CRUD 页面**。做完它，你就掌握了：
- 搜索区 + 表格 + 分页的联动
- 弹窗表单 + 校验 + 提交
- 删除二次确认
- 列表与详情的组件拆分

**后面 8 个页面，本质都是这一页的变体。** 所以这一页值得慢一点、吃透。

**第二阶段：点检项 + 巡检计划（3 天）**

结构和设备台账几乎一样，但字段不同。**这两个页面请你自己写**，这是最好的练习。

**第三阶段：巡检执行页（3–4 天）**

这是本系统最有业务价值的页面：一个设备 + 一组动态渲染的点检项 + 逐项录入 + 提交。

**第四阶段：统计看板（2 天）**

装 `echarts`，做 3 个图。

**第五阶段：Excel 导入导出（2 天）**

装 `xlsx`，导出设备清单。这是传统企业最看重的功能之一。

## 八、技术要点备忘

| 需求 | 方案 |
|---|---|
| 表格 + 分页 | `el-table` + `el-pagination`，注意「搜索条件变化要把 page 重置为 1」 |
| 表单校验 | `el-form` 的 `rules`，`validate()` 返回 Promise |
| 弹窗 | `el-dialog`，关闭时 `resetFields()` 防止脏数据 |
| 状态展示 | `el-tag` + 状态映射表（`label` / `type`） |
| 删除确认 | `ElMessageBox.confirm` |
| 导出 Excel | `xlsx` 库的 `utils.json_to_sheet` + `writeFile` |
| 图表 | `echarts`，注意容器要有确定高度 |

## 九、接口对接说明

当前项目**没有后端**，`src/api/device.ts` 里直接操作内存假数据。

等后端就绪后，只需把函数体换成：

```ts
return request<PageResult<Device>>({ url: '/device/page', method: 'get', params: query })
```

**页面代码一行都不用改。** 这就是「API 层」存在的意义——把「数据从哪来」和「页面怎么显示」隔开。
